# Elderly Care Chatbot — ML Intent Classifier Implementation Plan

This document describes a staged implementation for adding a **non-LLM intent classifier** to the existing Elderly application. It is written as a practical handoff for Codex.

## 1. Goal and boundaries

For the first version, the model only classifies a user's question. It does not query the database, interpret medical measurements, or generate the final answer.

Example:

Input:
`Is mom taking her medicines on time?`

Output:
```json
{"intent":"medicine_timing","confidence":0.94}
```

The confidence above is illustrative; use the actual model output.

Architecture:

```text
User question
    |
    v
Python classifier: TF-IDF + Logistic Regression
    |
    v
intent + confidence
    |
    v
Existing TypeScript/Express backend
```

Later, the backend will use the intent to call existing medicine/health services and build a factual response.

### Non-goals for this first pass

- No LLM, Gemini, Ollama, RAG, embeddings, or vector database.
- No separate medication-prediction model.
- No database access from Python.
- No patient health records sent to the classifier.
- No changes to the existing `/api/ai/chat` implementation.
- No frontend work until the model and backend API work.

## 2. Repository-specific observations

The supplied repository ZIP contains a TypeScript/Express backend with Mongoose and existing modules for medicine, medicine logs, health checks, health trends, and AI.

Relevant existing modules include:

- `backend/src/ai/` — existing LLM-oriented implementation; leave it untouched initially.
- `backend/src/medicine/`
- `backend/src/medicine-logs/`
- `backend/src/health-check/`
- `backend/src/health-trend/`
- `backend/src/middleware/auth.middleware.ts`

The main server is `backend/server.ts`, which wires services, controllers, and routers. Follow the project's existing conventions when registering the new router.

The existing medicine logs and health records should be reused in a later phase; do not duplicate their database logic in this first phase.

## 4. Initial intents

Start with eight supported intents:

| Intent | Meaning |
|---|---|
| `medicine_today` | Ask whether medicine was taken today |
| `medicine_missed` | Ask about missed/skipped doses |
| `medicine_timing` | Ask whether medicines are taken on time |
| `medicine_pattern` | Ask about recurring medication patterns |
| `sugar_trend` | Ask about blood sugar trends |
| `bp_trend` | Ask about blood pressure trends |
| `weight_trend` | Ask about weight changes |
| `health_summary` | Ask for an overall recent health summary |

Also support `unknown` as an inference result when the model is uncertain. It does not need to be a normal training class in the first version; use a confidence threshold to map low-confidence predictions to `unknown`.

Include varied wording, grammar, question length, and references such as “mom”, “mother”, “she”, and “the patient”. Avoid duplicating the same sentence with only a tiny word change. Do not include real patient data.

## 7. `train.py` requirements

Create `ml/intent-classifier/train.py`. It must:

1. Resolve all paths relative to the script file, not the shell's current directory.
2. Load `data/intents.csv`.
3. Validate that `text` and `intent` columns exist.
4. Remove empty/invalid rows and report how many rows remain.
5. Check that every intended class has enough examples for a stratified split.
6. Split data reproducibly into training and test sets (fixed `random_state`).
7. Fit `TfidfVectorizer`, with a reasonable initial configuration such as `ngram_range=(1, 2)`.
8. Train `LogisticRegression` with a sufficient `max_iter`.
9. Print accuracy and a per-class precision/recall/F1 classification report.
10. Save the fitted classifier to `models/intent_model.joblib`.
11. Save the fitted vectorizer to `models/tfidf_vectorizer.joblib`.
12. Create the `models/` directory if it does not exist.

Use a proper train/test split. Do not report training accuracy as test accuracy. Small or synthetic datasets can produce misleadingly high scores, so describe results honestly.

Suggested flow:

```text
CSV -> clean/validate -> train/test split -> TF-IDF -> Logistic Regression
    -> evaluation -> save classifier + vectorizer
```

## 8. `predict.py` requirements

Create `ml/intent-classifier/predict.py`. It must:

1. Accept exactly one question argument from the command line.
2. Reject an empty question.
3. Resolve model paths relative to the script.
4. Load the saved classifier and vectorizer.
5. Transform the question using the saved vectorizer.
6. Predict the most likely intent and its probability.
7. Apply a configurable confidence threshold (initial default: `0.70`).
8. Return `intent: "unknown"` if the top probability is below the threshold.
9. Print **only one JSON object** to stdout.
10. Send diagnostics/errors to stderr and exit non-zero if inference fails.

Example:

```bash
python predict.py "Is mom taking her medicines on time?"
```

Example output:

```json
{"intent":"medicine_timing","confidence":0.83}
```

Low-confidence output:

```json
{"intent":"unknown","confidence":0.42}
```

Probabilities from Logistic Regression are not necessarily well-calibrated measures of real-world certainty. Treat the threshold as a tunable engineering setting and validate it with held-out examples. Unknown-intent handling needs dedicated tests.

## 9. Train and test the standalone module first

From `ml/intent-classifier/`:

```bash
python -m venv .venv
```

Activate the environment, then run:

```bash
pip install -r requirements.txt
python train.py
python predict.py "Did mom take her medicine today?"
python predict.py "Which medicines did she miss?"
python predict.py "Is she taking her medicines on time?"
python predict.py "Has her blood pressure increased recently?"
python predict.py "How has her sugar been recently?"
python predict.py "Tell me a joke"
```

Check that the model artifacts exist and that the script returns valid JSON. Do not expect a particular confidence value. Inspect mistakes and improve the training examples before integration.

## 10. Why not create a binary yet?

Do not start with PyInstaller or an `.exe`. Initially the backend should invoke Python directly. This is easier to develop and debug:

```text
Node backend -> spawn(python, [predict.py, question]) -> JSON stdout
```

If deployment later requires a self-contained executable, package it after the pipeline works and adjust the configured executable path. A `.joblib` model is a serialized model artifact, not itself an executable binary.

## 11. Backend bridge — Phase 2

Only after the Python CLI works, create `backend/src/chatbot/`.

### `chatbot.types.ts`

Define the known intent union and request/response types. Example:

```ts
export type ChatbotIntent =
  | 'medicine_today'
  | 'medicine_missed'
  | 'medicine_timing'
  | 'medicine_pattern'
  | 'sugar_trend'
  | 'bp_trend'
  | 'weight_trend'
  | 'health_summary'
  | 'unknown';

export interface ChatbotIntentRequest {
  question: string;
}

export interface IntentPrediction {
  intent: ChatbotIntent;
  confidence: number;
}
```

Adapt naming and validation style to existing project conventions. Validate the Python response at runtime rather than trusting its shape.

### `chatbot.service.ts`

Create a service that invokes the Python classifier:

- Use Node's `child_process.spawn`.
- Pass the question as an argument; do not build a shell command from user input.
- Prefer `shell: false`.
- Resolve the Python script path using `import.meta.url`/`fileURLToPath` or another path strategy compatible with the project's ESM setup; do not rely on whichever directory the server was launched from.
- Configure the Python executable and optional script path with environment variables, e.g. `CHATBOT_PYTHON_EXECUTABLE` and `CHATBOT_PREDICT_SCRIPT`.
- Collect stdout and stderr separately.
- Set a timeout and terminate a stuck child process.
- Handle spawn errors, non-zero exit codes, malformed JSON, and oversized output.
- Validate that `intent` is one of the allowed values and `confidence` is a finite number between 0 and 1.
- Return a typed result or throw a controlled service error.
- Do not log the full user question or any patient data unnecessarily.

Do not use `exec(\`python predict.py "${question}"\`)`; shell interpolation is unnecessary and unsafe.

### `chatbot.controller.ts`

Add an endpoint that accepts:

```http
POST /api/chatbot/intent
Content-Type: application/json
```

Request:

```json
{"question":"Is mom taking her medicines on time?"}
```

Response:

```json
{"intent":"medicine_timing","confidence":0.83}
```

Validate the body using the project's existing Zod conventions. Return appropriate 400 errors for invalid input and controlled 5xx errors if the classifier is unavailable. Do not return stack traces to clients.

### `chatbot.router.ts`

Register the endpoint using the existing router conventions. Register the new router in `backend/server.ts` following the existing service/controller/router dependency-wiring pattern.

For this first classifier-only endpoint, authentication policy should follow the application's existing conventions. Before any endpoint retrieves patient-specific records, require authentication and enforce patient access. Do not accept a client-supplied patient ID as proof of authorization.

## 13. Later intent-to-data dispatch (not Phase 1)

Once intent classification is working, the backend can map each intent to existing services:

| Intent | Later backend work |
|---|---|
| `medicine_today` | Query today's authorized patient's medicine logs |
| `medicine_missed` | Count and list missed/skipped records over a defined period |
| `medicine_timing` | Compare scheduled and taken times using a documented tolerance |
| `medicine_pattern` | Aggregate adherence by time of day, weekday, medicine, etc. |
| `sugar_trend` | Read health records and summarize recorded sugar values |
| `bp_trend` | Read BP values and describe the observed trend |
| `weight_trend` | Read weights and describe the observed trend |
| `health_summary` | Reuse the existing health-trend summary service where appropriate |

Distinguish `Missed`, `Skipped`, `Pending`, and `Taken` according to the application's actual status semantics. Do not silently combine statuses. Do not claim that correlation proves causation or present trend detection as a medical diagnosis.

## 16. Acceptance criteria

Phase 1 is complete when:

- `python train.py` runs successfully from the module directory and another working directory.
- Both model artifacts are created.
- `python predict.py "Is she taking medicines on time?"` emits one valid JSON object.
- Multiple examples map to sensible intents.
- An unrelated question can be mapped to `unknown` when below the chosen threshold.
- Evaluation results are actual measured results, not example numbers.

Phase 2 is complete when:

- The backend endpoint invokes Python successfully.
- The response is validated JSON with an allowed intent and confidence.
- Invalid input, missing model, malformed output, timeout, and process failure are handled safely.
- Existing routes and the existing LLM implementation remain unchanged.
